# appGacha 设计总览与决策记录

> 状态：设计阶段 · 最后更新 2026-07-16

## 1. 问题与定位

**痛点**：对小白来说，难的从来不是"让 AI 写出代码"，而是代码之后的一切——运行环境、数据持久化、Node/端口等概念、迁移分发。AI 生成能力已经商品化，但"生成物的运行时"没有人给小白解决。

**定位**：appGacha 把"生成 + 持久运行时 + 可迁移"打包成一个傻瓜盒子。用户填写愿望单（例如"我想要一个背单词软件"），后台智能体按严格规范孵化出插件（扭蛋 `.egg`），扭蛋在主应用提供的沙箱中运行，拥有自己的数据库和文件空间，整个文件夹可拷贝迁移。

**差异化**：三者的交集，砍掉任何一个都掉回已有产品的领域。

- uTools/Rubick：有插件运行时，无 AI 生成
- Claude Artifacts：有 AI 生成，无持久化与本地能力
- appGacha：生成 + 持久运行时 + 可迁移，且蛋**天生 AI**（见决策 D4）

**扭蛋隐喻的价值**：天然设定"结果有随机性、不满意可以再抽"的心理预期，为生成不完美兜底。

## 3. 核心决策记录

### D1 沙箱 + 能力桥接，不给蛋真实 Node 环境

沙箱不是安全选项，而是产品本身：

1. **沙箱是"可迁移"承诺的前提**。真实 Node 环境意味着 node_modules、native 依赖、版本要求——换台机器就把"环境问题"这个原始痛点还给用户。纯 HTML/JS + bridge 的蛋才是 copy 即运行。
2. **沙箱是生成成功率的前提**。封闭的目标 API 可以在系统提示里穷举、可以自动校验；"可以 require 任何包"是不可校验的世界。
3. **能力不够时，扩展主应用而不是打开沙箱**。每个新能力都是审核过、文档化、智能体可靠掌握的 bridge API（uTools 验证过的路线）。

例外场景（后台常驻逻辑）用"主应用代跑"解决：manifest 声明 `schedule`，主应用调度执行蛋提供的受限 JS，蛋不自己起进程。

### D2 生成管线基于 Claude Agent SDK，工程收窄

复用现有优秀智能体产品，不自建 agent loop。工程控制点：

- **收窄工具面**：智能体只有对蛋文件夹的读写、`validate_egg`（manifest schema 校验 + 静态检查是否越出 bridge API）、`test_egg`（无头 Electron 运行、截图、收集 console 报错）。
- **脚手架优先于自由生成**：提供蛋模板（manifest 骨架、`egg.d.ts` 类型声明、示例代码），让智能体做填空题。类型声明是把 API 规范喂给智能体的最佳载体。
- **验收闭环在管线内，不在用户面前**：生成 → validate → 无头运行 → 截图自查 → 不合格自动迭代（上限 3 轮），超限才抛"这个蛋没孵好，再抽一次？"。
- 小白不会调试，孵化质量闭环是"小白可用"承诺兑现的关键。

### D3 模型接入双轨制

Agent SDK 只要求 Anthropic 兼容接口，不绑定模型。DeepSeek 官方提供 Anthropic 兼容 API，直接指 base URL 即可；必要时经 LiteLLM 等网关接任意模型。

- **MVP**：用户自配 API（key + base URL）。
- **商业化阶段**：默认托管（如 DeepSeek 转售，按百分比浮动加价作为利润）。托管顺便解决小白配置门槛，且蛋的运行期 AI 调用（见 D4）让利润来自蛋的整个生命周期而非孵化一次。
- 托管牵扯账号、支付、防滥用，是另一个量级的工程，MVP 不做。

### D4 蛋天生 AI（`egg.ai`）

主应用手里已握着模型通道，`egg.ai` 把通道桥接给蛋——蛋不需要 key、不需要 SDK。这是市面上没有的东西：小白许愿得到的不是"死"程序，而是自带智能的活物。

| 愿望 | 无 AI 的蛋 | 天生 AI 的蛋 |
|---|---|---|
| 背单词 | 卡片翻转 | 自动生成例句/助记/近义词辨析 |
| 记账本 | 手填表单 | 粘贴"昨天买菜38"自动结构化入账 |
| 日记本 | 文本框 | 每周自动生成情绪回顾 |
| 作文练习 | 存文档 | 内置批改和润色 |
| 课程表 | 手动录入 | 粘贴课表文本自动解析 |

接口形态与约束见 egg-spec。

### D5 蛋的进化 = 外部"许愿升级"，仪式感优先

蛋不做内部自迭代。进化入口在主应用层面：蛋架上每个蛋有"许愿升级"按钮，用户对着蛋许愿（"加个夜间模式"），孵化器拿 manifest 中留存的原始 `wish` + 现有代码做增量进化。

**理由**：外部许愿保持了扭蛋的仪式感——升级也是一次"抽"，与产品隐喻一致；同时进化逻辑集中在孵化器，蛋保持纯粹的运行物。

配套约束：**每次升级前自动整蛋备份**（数据 schema 迁移是最容易丢数据、最伤信任的环节）。

### D6 v1 能力清单的划线标尺

不追求 API 面最小，而是：**把杀手级愿望单 Top 10 摊开，缺了会让蛋从"惊艳"掉到"玩具"的能力就进 v1。** 结论：提醒类愿望（背单词提醒、番茄钟）是小白需求重灾区，`notify` + `schedule` 必须进 v1；具体清单见 egg-spec。v1 约 8 个能力域，仍是智能体一份文档能吃透的规模。

## 4. 路线图（设计→实现顺序）

1. **`.egg` 规范 + bridge API v1**（已定稿，见 docs/egg-spec.md）
2. **蛋运行时**：webview 隔离、preload 注入、权限拦截
3. **孵化器**：Agent SDK 工具集、蛋模板、验收闭环
4. **蛋架 UI + 蛋管理器**（前三步可用命令行验证，UI 最后做）

模型托管计费推迟至商业化阶段。
