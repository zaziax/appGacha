# AppGacha 项目评估与出海验证报告

> 评估日期：2026-08-18  
> 评估重点：`appGacha` 桌面应用  
> 范围：产品定位、用户体验、技术架构、安全、工程质量、开源商业化、出海策略与邀请制 Beta。服务端和官网仅作为桌面端依赖背景。

## 1. 执行摘要

AppGacha 已经超过概念 Demo 阶段。它最有价值的部分，不是 3D 扭蛋机本身，而是把“AI 生成代码”重新定义成“生成一个能长期活在桌面、拥有本地数据和系统能力、可以升级和迁移的小应用”。

综合评价为 **6.7/10：有明确产品灵魂、架构基础扎实的强 Alpha，适合进入邀请制 Beta，但尚不适合大规模公开发布。**

项目值得继续构建，但下一阶段必须从“扩充功能”切换到“证明可信度”：

1. 证明普通用户可以顺利得到第一颗可用蛋。
2. 证明相同愿望可以稳定产出，不是偶尔惊艳。
3. 证明用户会在生成之后持续使用同一颗蛋。
4. 证明第三方蛋、AI 消耗和本地数据值得用户信任。

当前建议：

- 继续投入，并给项目一个 6～8 周的集中验证周期。
- Windows 优先，暂缓同时承担 macOS/Linux 的公开质量承诺。
- 完成安全、质量基线后，分批招募 30～40 名测试者。
- 邀请资格应限制官方托管 AI 和云服务，不应限制开源客户端本身。
- 如果用户只喜欢“扭出来的那一刻”，却不在七天后继续使用生成结果，应立即缩小品类或调整定位。

## 2. 产品定位与价值判断

### 2.1 核心定位成立

项目将桌面差异化归纳为桌面形态、持续存在、本地数据和局域网联机，方向是完整而自洽的，详见 [desktop-value.md](desktop-value.md)。

AppGacha 的合理定位不是“另一个 AI 编程工具”，而是：

> 为普通人生成并长期运行个人桌面小应用的安全运行时。

这一定义把它与生成网页、生成代码仓库或面向开发者的本地 AI Builder 区分开来。用户最终得到的应该是可直接使用的小应用，而不是需要继续进入 IDE、配置依赖和部署的项目。

产品最重要的差异化包括：

- 不需要 npm、终端、部署或 GitHub。
- 每颗蛋运行在统一、可约束的宿主环境中。
- 数据本地持久化，整个蛋可以导入、导出和迁移。
- Widget、托盘、提醒和开机自启让应用真正存在于桌面。
- 用户通过“许愿升级”继续演进应用，不必修改源码。
- Bridge API 把数据库、文件、AI、通知、定时和联机能力变成可验证契约。

### 2.2 扭蛋隐喻有价值，也有出海风险

扭蛋隐喻能自然表达生成的不确定性，并统一生成、失败、重试、收藏和升级的产品语言，这是良好的产品设计。

但 `Gacha` 在海外也容易让用户联想到抽卡、Loot Box 和随机付费。因此建议：

- 保留 AppGacha 作为有记忆点的品牌候选。
- 英文产品文案主要使用 `mini-app`、`capsule`、`personal app`。
- 不按“抽一次”收费，不把 AI 额度包装成随机抽奖硬币。
- 明确强调应用和数据归用户所有，可以重试、升级和迁移。
- 在早期落地页测试 AppGacha 名称是否造成负面理解。

推荐英文定位：

> Wish for a tiny app. Keep it on your desktop.

或：

> AppGacha turns a wish into a portable mini-app that lives on your desktop.

### 2.3 竞争已经出现，不能只依靠“本地、开源、AI 生成桌面应用”

截至评估日期，Dyad 已经把自己定义为本地开源 AI App Builder，并形成较大的开源社区；App Generator 也明确提供自然语言生成、测试和打包 Electron 桌面应用的能力。

参考：

- [Dyad 官方仓库](https://github.com/dyad-sh/dyad)
- [App Generator 官网](https://app.website-generator.net/)

因此 AppGacha 不应与这些产品比较“能生成多复杂的项目”，而应强化：

- 面向非程序员，而不是面向 Power User。
- 生成结果是运行物，不是开发项目。
- 安全运行时、持久数据和桌面生命周期是产品主体。
- 小应用生成、持续使用和迁移的体验比代码自由度更重要。

## 4. 技术与工程评估

### 4.1 值得肯定的架构

蛋窗口使用独立持久化分区，并启用了 Electron 沙箱、上下文隔离和关闭 Node 集成，参见 [`eggWindow.ts`](../src/main/eggWindow.ts)。协议层设置 CSP、默认断网和浏览器权限拒绝，参见 [`protocol.ts`](../src/main/protocol.ts)。

能力调用由主进程根据真实 `webContents.id` 查找蛋身份并检查 manifest 权限，没有信任渲染进程自报身份，参见 [`capabilities/index.ts`](../src/main/capabilities/index.ts)。

数据库在可强杀的独立进程中执行，并限制危险 SQL、结果行数、结果字节数和执行时间。这说明项目确实把 AI 生成代码视为不可信输入，而不是仅依赖前端隔离。

生成系统也形成了比较完整的工程闭环：

- staging 装配目录
- 收窄的工具集
- 回合、token 和时间预算
- 静态校验
- 离屏运行、白屏检测、控制台错误和截图
- 失败归档和断点续建
- 升级前备份和回滚

当前机芯限制为 60 回合、30 万 token、15 分钟和最多三轮修复，参见 [`fcDriver.ts`](../src/main/fcDriver.ts) 与 [`pipeline.ts`](../src/main/pipeline.ts)。动态验收使用正式蛋运行环境，参见 [`test.ts`](../src/main/test.ts)。

### 4.2 本次验证结果

本次审阅实际执行了生产构建与现有测试：

- TypeScript 与前端生产构建成功。
- 默认单测为 55 项通过、1 项超时。
- 将测试超时放宽至 15 秒后，56 项全部通过。
- 超时点位于 JSON KV 存储的 1000 键压力场景，说明断言逻辑正确，但实现存在反复读取、序列化并重写整份文件的性能退化。
- Vite 主 JS 产物约 1.48 MB，已触发大 chunk 警告。
- 当前 Windows 解包发布目录约 457 MB，作为个人桌面工具偏重。
- 数据库集成测试和 Electron 冒烟测试受评估环境 GPU/缓存权限限制而未能完成，不能据此判定应用代码失败。

现有测试主要覆盖 storage、fs、zip、AI 参数和 SQL 守卫，参见 [`tests`](../tests) 与 [`vitest.config.ts`](../vitest.config.ts)。导入、协议、管线、升级、同步、认证、调度、UI 和权限授权仍缺乏系统性回归测试。

发布工作流目前在打标签后直接构建和上传，没有先执行 `test:all` 或 Electron smoke，参见 [`release.yml`](../.github/workflows/release.yml)。正式发布前还需要 Windows 代码签名、macOS notarization 和第三方许可证清单。

### 4.3 可维护性风险

当前约有 80 个源码文件、1.5 万行非 vendor 源码，但多个核心文件已过大：

- `MachineView.tsx`：约 1221 行
- `fcDriver.ts`：约 937 行
- `shelf.ts`：约 750 行
- `pipeline.ts`：约 641 行

其中 `shelf.ts` 同时承担蛋管理、生成、设置、认证、计费、同步和更新 IPC，已经接近“修改任意业务都可能影响全局”的阶段。

建议：

- 按蛋管理、生成、账号、计费、同步、更新拆分 IPC 注册器。
- 将 `MachineView` 拆成步骤状态机和独立视图组件。
- 将 `fcDriver` 拆为模型传输、上下文管理、工具执行和质量闸门。
- 3D 场景动态加载，增加二维和低 GPU 降级模式。
- 增加 `prefers-reduced-motion`、键盘操作和可访问性测试。

## 5. 安全与隐私重点

### 5.1 第三方 `.gacha` 导入链路需要优先加固

当前导入流程为解包、读取基础 manifest、直接注册，并立即加载包内定时任务，参见 [`shelf.ts`](../src/main/shelf.ts) 和 [`gachaPkg.ts`](../src/main/gachaPkg.ts)。

主要风险：

- 解包没有总展开体积、单文件体积和条目数量限制，存在压缩炸弹和磁盘占满风险。
- 导入时未执行完整 `validateEgg` 与离屏 `testEgg`。
- manifest 声明权限基本等于自动获得，缺少用户权限确认。
- 包内 `schedule.json` 可在导入后立即装载。
- 第三方蛋可以声明自动启动。
- 每颗蛋的 session 允许所有 `egg://` 地址，建议将 session 与固定 eggId 强绑定，并禁止跨蛋顶层导航。

推荐导入流程：

> 限额解压 → 完整静态检查 → 离屏试跑 → 展示来源与权限 → 用户确认 → 正式注册

第三方蛋的 AI、网络、定时任务和自启动应默认关闭，待用户逐项授权。

### 5.2 AI 权限同时也是消费权限

蛋内 AI 当前有每蛋每分钟调用限制，但 `maxTokens` 缺少宿主侧钳制，也没有每蛋消费预算，参见 [`capabilities/ai.ts`](../src/main/capabilities/ai.ts)。

建议增加：

- 宿主侧最大输入和输出 token 限制
- 每蛋每日/月度预算
- 第一次使用 AI 时授权
- 每次生成和蛋内调用的预计/实际消耗展示
- 一键禁止某颗蛋使用 AI
- 平台级全局异常消耗熔断

### 5.3 日志可能记录私人内容

机芯会把用户愿望、模型完整思考内容和工具参数预览写入 `app.log`，参见 [`fcDriver.ts`](../src/main/fcDriver.ts) 与 [`log.ts`](../src/main/log.ts)。

建议默认只记录：

- 阶段、耗时、token、模型和错误码
- 脱敏后的愿望摘要
- 工具名称和成功/失败状态

完整模型内容应由开发日志开关显式启用；提交诊断信息前必须让用户预览并确认。

## 6. 开源与商业化建议

### 6.1 推荐结构

“开源客户端 + 云端增值服务”适合 AppGacha 的本地优先定位。

| 层 | 建议开放程度 |
|---|---|
| 桌面客户端 | 开源 |
| `.gacha` 格式、Bridge API、模板、验证器 | 开源并鼓励兼容实现 |
| 托管 AI 网关、计费、防滥用、同步服务 | 可保持闭源 |
| AppGacha 名称、Logo、官方签名和官方云 | 通过商标和服务身份保护 |

当前 MIT 许可证可以继续使用，但必须接受其允许他人商业使用、修改和闭源再发布的事实。真正的防线应是官方生成质量、品牌、云服务、兼容性、签名体系和社区，而不是阻止代码被复制。

建议补充：

- `TRADEMARK.md`
- `SECURITY.md`
- `CONTRIBUTING.md`
- 第三方许可证与 NOTICE
- 有外部贡献后再评估 DCO/CLA

### 6.2 免费版与 Pro 的合理边界

免费版应保持完整可信：

- 本地生成与运行
- BYOK
- 导入导出
- 本地持久数据
- 基础 Bridge API

Pro 可以提供：

- 免配置托管 AI
- 跨设备同步
- 云备份与版本历史
- 误删恢复
- 官方签名蛋与精品蛋库
- 更稳定、更快或质量更高的生成通道

不建议提供不可控的“无限 AI”订阅。更稳妥的结构是订阅包含固定额度，超出后按量充值，并为每颗蛋提供消费上限。

AI 托管主要解决首次使用门槛，不应被视为核心护城河。云同步若只有“同步”也可能付费意愿不足，应与备份、历史版本、恢复和官方可信生态组合成长期价值。

## 7. 是否继续构建：验证条件

项目值得继续，但应该设置明确的继续、聚焦和停止条件。

建议用 6～8 周完成一次验证：

| 指标 | 建议目标 |
|---|---:|
| 测试者总数 | 30～40 人 |
| 非程序员测试者 | 至少 20 人 |
| 无人协助完成第一颗可用蛋 | ≥70% |
| 七天内再次打开同一颗蛋 | ≥50% |
| 主动生成第二颗或许愿升级 | ≥30% |
| 愿意真实付费 | 至少 5 人 |
| 金标愿望语义达成率 | 约 80% |

应额外记录：

- 首次出蛋率与最终健康率
- 按愿望类型、模型和版本划分的语义任务达成率
- 中位/P95 生成时间、token 和成本
- 用户保留、删除和再次打开的蛋类型
- 用户真正愿意长期使用的前三类愿望

最重要的负面信号是：

> 用户喜欢生成过程，但不保留、不复用生成结果。

若出现这一信号，说明产品仍偏 Demo，应立即聚焦到留存最高的一两个品类，而不是继续扩充通用能力。

## 8. 个人开发者出海策略

### 8.1 Windows 优先

Beta 阶段只对 Windows 做正式承诺。这样可以减少安装、签名、GPU、文件关联、托盘和原生模块在三套平台上的维护成本。等 Windows 留存成立后，再恢复 macOS；Linux 可继续允许社区从源码运行，但不承诺同等级支持。

### 8.2 不要同时维护过多社区

Beta 初期建议只使用：

- GitHub Discussions：公告、Q&A、建议和投票
- 一个英文 Beta 申请表
- 一个支持邮箱
- 应用内反馈入口

GitHub Discussions 适合把开放讨论转成 Issue，参考 [GitHub Discussions 官方文档](https://docs.github.com/en/discussions/collaborating-with-your-community-using-discussions/about-discussions)。达到约 50 名活跃测试者并开始出现用户互助后，再考虑 Discord。

### 8.3 Beta 申请表

建议收集：

- Windows 版本
- 职业或日常使用场景
- 最想生成的一个桌面小应用
- 是否愿意使用自己的 API Key
- 是否愿意参加 20 分钟访谈
- 是否允许发送匿名诊断信息
- 使用过哪些 AI App Builder
- 如果产品解决问题，愿意支付多少

最重要的问题是：

> What small personal tool do you wish existed on your desktop?

这既能筛选测试者，也能直接形成真实愿望数据集。

## 9. 邀请制 Beta 渠道与节奏

### 9.1 第一批：10 名技术型测试者

目标是发现安装、安全、兼容、崩溃和日志问题，不用于验证大众需求。

渠道：

- GitHub README 顶部增加 `Apply for Beta`
- GitHub Discussions 置顶 `Beta Cohort #1`
- Reddit `r/alphaandbetausers`
- Reddit `r/SideProject`
- GitHub 允许自推广的集中帖
- 定向联系 local-first、Electron、桌面 Widget 和 AI Builder 开发者

### 9.2 第二批：15～20 名目标用户

不要只在独立开发者圈招募。建议选择三个使用场景，每类 5～7 人：

- 学生：复习计划、番茄钟、背单词、公式卡
- 知识工作者：悬浮清单、笔记、数据转换、提醒
- 个人管理：记账、习惯追踪、简单表格和报表

渠道与方法：

- 进入相关 Reddit 社区前先确认自推广规则或联系管理员。
- 寻找中小型生产力、学习工具类 YouTube 创作者。
- 在 X、Bluesky、YouTube Shorts 发布 30～45 秒真实生成视频。
- 定向联系公开表达过具体小工具需求的用户，避免批量冷私信。
- 给每名测试者明确任务，并要求使用一周，而不是“随便玩玩”。

推荐英文招募文案：

> Tell AppGacha one small tool you wish existed. It builds a portable desktop mini-app for you. I’m looking for Windows users willing to use their app for one week and tell me what broke.

### 9.3 第三批：Show HN 技术公开 Beta

Show HN 适合已经可以直接下载和尝试的产品，不适合只有 Waitlist 的页面。官方建议尽量避免注册或邮箱障碍，参考 [Show HN Guidelines](https://news.ycombinator.com/showhn.html)。

标题可以采用：

> Show HN: AppGacha – wish for a portable mini-app that lives on your desktop

页面应提供：

- 一键下载
- GitHub 源码
- 30 秒演示
- 三个示例蛋
- 沙箱和数据所有权说明
- 不登录也能使用的 BYOK 或演示路径

由于客户端开源，邀请码只应限制官方托管 AI、同步和云服务，不能真正限制本地客户端。

### 9.4 Product Hunt 放到公开 Beta

Product Hunt 当前更强调已经可以使用的产品，纯 Waitlist 产品通常不会获得推荐，除非能立即提供访问，参考 [Product Hunt Featuring Guidelines](https://help.producthunt.com/en/articles/9883485-product-hunt-featuring-guidelines)。

建议顺序：

1. GitHub 小规模内测
2. 定向非技术用户测试
3. Show HN
4. 根据反馈修复 2～4 周
5. Product Hunt 公开 Beta

## 10. 建议的近期路线图

### 第 1～2 周：可信度基础

- 加固 `.gacha` 解包和导入权限确认。
- 增加 AI token、额度和每蛋预算。
- 默认关闭完整 AI 内容日志。
- 完成现有十条金标愿望的语义探针。
- 修复 storage 1000 键性能问题或调整能力定位。
- CI 强制执行 build、unit、db integration 和 smoke。

### 第 3 周：Beta 准备

- Windows 签名安装包。
- 英文落地页与 30～45 秒演示视频。
- GitHub Discussions、`SECURITY.md`、`CONTRIBUTING.md`。
- Beta 申请表、匿名遥测选择和云端数据删除入口。
- 准备 3～5 颗高质量示例蛋。

### 第 4～5 周：技术测试

- 每周放入 5 名技术测试者。
- 优先修复安装、崩溃、权限和数据丢失问题。
- 不增加新的大能力。

### 第 6～8 周：目标用户验证

- 分三个场景招募非技术用户。
- 记录首次成功率、七日复用率和真实付费意愿。
- 根据留存最高的愿望类型决定下一阶段聚焦方向。

## 11. 最终结论

AppGacha 值得继续做。真正有辨识度的核心不是动画、3D 或能力数量，而是：

> 把 AI 生成结果限制在一个可验证、可持久化、可迁移、具有桌面能力的运行时里。

这条路线在产品上成立，现有代码也已经证明它在工程上可实现。

接下来的胜负不在于继续增加 vendor、Bridge API 或视觉效果，而在于：

- 普通用户能否无需复杂配置就得到第一颗有用的蛋。
- 相同愿望能否稳定产出。
- 用户是否会在七天后继续使用同一颗蛋。
- 用户是否敢于保存数据、导入别人分享的蛋并允许其消耗 AI 额度。

因此建议项目从“功能建设期”正式切换到“可信度建设期”。完成安全与质量 P0 后进入邀请制 Beta；在真实复用率得到证明前，不进行大规模公开推广。
